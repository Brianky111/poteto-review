# Poteto Review 审阅标尺、四大模式与输出模板

按目标类型选择唯一主模式（可叠加审阅 `Diff + 测试`），严格使用统一分级标签与输出模板交付结论。

---

## 一、分级标签定义（Severity & Tag Taxonomy）

| 标签 | 判定标准（什么时候打这个标） | 默认处置意见 |
|---|---|---|
| `MUST KILL` | 1) 为权宜补丁辩解的借口注释（不在 5 类例外内）；2) 屏蔽真实正确性/安全报错的 Lint 或类型压制符；3) 死代码、已迁移完仍保留的旧兼容壳、单实现多余抽象；4) 同义反复假测试（改坏行为仍绿 / 仅断言自造 Mock） | 删除、移除压制符并直面报错，或彻底重写/删掉假测试 |
| `MUST RESHAPE` | 1) 用空 `catch`、`??` 兜底、`setTimeout`/`rAF`、重试掩盖非法状态；2) 多头状态管理无唯一拥有者（SSOT）；3) 内部函数重复防御校验却未在系统边界解析定型；4) 跨进程/跨层耦合导入；5) 膨胀为高耦合巨石文件 | 从根因处重构状态边界、收敛防呆 API 或拆清目录归属 |
| `PROSE DEBT` | 1) 可被架构、类型、依赖图检查或 Lint 拦截的规则，却只写在 `AGENTS.md`/Rules/Skill/PR 提醒里；2) 单次局部纠正被 Agent 过度泛化成全仓铁律；3) 提示词肥胖重复、缺少渐进披露 | 下沉为可执行的静态/运行时检查或精简至人工判断要点 |
| `FAKE PROOF` | 用“构建成功”“自测口头报告”“只含 Mock 的单测”或“仅测 `/health` / 200 状态码”充当交付验证，缺少真实用户路径证据与产物新鲜度保证 | 补齐驱动型真实行为验证（驱动 CLI / 端到端链路 / 可复查产物）后才准过关 |
| `WEED BUFFER` | 审阅中顺手发现、但**不在本次变更范围内**的历史坏味道或潜在模式缺失 | **禁止当前 PR 顺手扩改**；记入缓冲清单/工单队列，凑齐 2 次同类模式再统一抽根 |

> **Comment-Sicko 五类法定保留例外**（除此之外注释默认清理或靠重写代码消除）：
> 1) 法律与许可证头；2) 非可控外部依赖、平台、协议或浏览器的真实怪癖（且已核实今天仍存在）；3) 定义公共 API 契约的文档注释；4) `prettier-ignore` 等纯格式化抑制；5) 代码自身无法表达的 Issue / RFC 追踪链接。

## 二、四大专门审阅模式

### Mode A — PR / Diff / 代码变更审阅

1. **原子性与可验证序列**：PR 是否只围绕单一可解释目标？先删后加、先挂失败测试/契约再落实现（`sequence-verifiable-units`）还是把重构、业务变更、顺手清理混成一锅？
2. **状态唯一拥有者与最小知识原则**：新增或修改的状态是否只有一个权威写入点？调用方是否被迫了解内部时序或底层实现细节？
3. **系统边界 vs 内部信任**：外部输入（HTTP、CLI、配置、DB 行、RPC）是否在边界处一次性解析成清晰领域类型，并在内部函数消除冗余空值防御？
4. **反症状补丁与反借口注释**：核对 `poteto_audit.py --diff` 报出的 `suppressions`、`alibi_comments`、`symptom_guards`；逐个追问“若删掉这个 catch/timer/ignore，哪一个设计缺陷会暴露？”
5. **Diff 中新增测试的双编辑检查**：每条新增测试是否在破坏行为时必红、改重构实现细节时不脆碎？
6. **行为产物与门类判断**：对于功能变更，是否存在对应真实运行结果（界面、CLI 输出、状态图或验证日志）？是否触及权限、迁移、资金、密钥等单向门？

### Mode B — 仓库架构与代码库健康度审阅（Dune 体检）

1. **目录即上下文与最短路径**：目录命名是否直接揭示运行域/边界（如主进程 vs 渲染进程、服务端 vs 客户端、功能共置目录）？能否避免让新介入的 Agent 为改一个功能做全仓 `grep` 跨七八层文件夹？
2. **微妙“脚枪”API 是否收口**：工程中最容易被 AI 写错的高语义门槛原语（如不受控副作用钩子、原始 SQL/Shell 拼接、裸定时器、分散鉴权检查）是否通过框架封装与 Lint 限制在少数基础设施模块中？
3. **依赖边界与静态红线**：是否存在明确的依赖图/导入方向禁忌，使“往错地方导入”直接编译失败或 CI 打红，而非靠代码评审人肉盯防？
4. **花园杂草密度与演进路线诊断**：
   - 如果是**高约束老仓（Brownfield）**：排查未加棘轮的新增长杂草与可隔离演进区（类似 `clean_scopes` 分片净土），建议用“棘轮锁旧债 + 局部净土先零债”避免一刀切摊大饼；
   - 如果是**Vibe Coding 起步新仓（Greenfield）**：重点警惕毫无约束下迅速长出的巨石文件（>500 行）、重复粘贴逻辑与补丁注释堆叠，优先建议立骨架并减法整合。
5. **信任阶梯定位**：判断仓库当前更接近哪一档现状——手工人肉代理（低信任）、内环局部有护栏与实测 CLI（中信任）、全仓静动态闭环（高信任）或可安全自动跑外环（极高信任），指出当下卡在跨向下一档的唯一最大瓶颈。

### Mode C — 验证与测试套件审阅

1. **双编辑测试逐案审计**：找出“改坏功能居然还能过”的虚绿测试（常见病灶：用被测函数自己算预期结果、`expect(x).toBeDefined()` 敷衍断言、把 `spy/mock` 当测试本身，以及断言私有方法调用次序而非外显输出/外部副作用）。
2. **真验证 vs 代理验证**：应用仓库是否具备用户视角的 `feature-map`（或分片验证索引 `verify-<app>`），明确标明“用户路径 + 预期信号 + 已知假绿陷阱”？还是用 `/health`、单纯单元测试或编译通过冒充功能已通？
3. **确定性验证驱动是否从推理中剥离**：Agent 每次测页面或接口时，是在用固定 CLI / 脚本一次跑通（省 Token 且可测本身），还是每轮自己现场手敲一长串脆弱命令重新发明轮子？
4. **高风险空白区评估**：对并发竞争、重试幂等、多端状态流转、解析器、核心渲染算法等“错一次代价极高、单测覆盖不到”的局部，评估是否应补充 Property-Based Testing（UI/状态属性测试）、用户视角状态机可视化，乃至 TLA+ / Lean 形式化模型检查。

### Mode D — Agent 工作流 / Skill / `AGENTS.md` / 多 Bot 编排审阅（Dr. Eggbot 视角）

1. **散文肥胖与保质期审计**：检查 `AGENTS.md`、Rules、Skill 是否超过合理阅读预算或堆满“禁止/NEVER/MUST NOT”。凡能下沉为类型、脚本、Lint 的规则，一律判 `PROSE DEBT`；追问“6 个月后且换成更强模型时，这段死板步骤还会成立吗？有没有把一次偶发修正过度写成永久教条？”
2. **上下文窗口防守（Guard the Context Window）**：大日志、全仓扫描、交叉搜索是否通过确定性脚本或只读子 Agent 消化后只回传结构化摘要？Skill 是否合理分层渐进披露，而非开机一次性全量注入？
3. **角色单一性与派工纯粹性**：主管/协调型 Agent（如工程主管模式）是否真正只拆解调度并验收，还是“既当主管又自己闷头手写一长串烂代码”？单一 Bot 是否越肩兼职过多无关事务、到了需要拆出专职 Bot 或抽取共享 Skill 的临界点？子 Agent 推理预算是否按任务复杂度分级，而非全员顶配烧钱或简单调度浪费贵模型？
4. **Routine 与外环噪音控制**：高频定时唤醒（Routine）是否存在“发现一处改一处导致并发冲突/白烧 Token”的问题？是否先建立**缓冲汇总表（Buffer/Queue）**聚合共性问题后再批量治本？
5. **Skill 评测与改进防作弊审计（Eval & Hillclimb）**：评估 Skill 改动时，是否陷入自测自夸（同模型自评、目录或 Prompt 泄露 `eval/rubric/judge/benchmark/candidate` 字样诱发应试作弊、只听 Agent 口头自述“遵循了哪条原则”而不查代码与轨迹）？迭代优化（`hillclimb`）是否冻结基准并与回归门禁配对、单步验证未改善即整笔回退？

## 三、多 Agent 并行审阅编排（仅用户明确要求时启用）

默认单视角即可完成审阅。当面对大型 PR 或整仓深度体检、且用户**明确要求多 Agent 协同审阅**时，拆分为 3 个互不改代码的只读子 Agent 并行排查，最后由主审汇总去重：

1. **架构与根因审计员**：专攻刀 1/2/3/6（目录边界、状态所有权、症状补丁、巨石模块、单双向门）。
2. **Comment-Sicko 反借口猎手**：专攻刀 4（对照 `poteto_audit.py` 输出与 diff 逐行审判注释、压制符与可清理死代码）。
3. **验证与 Agent 系统审计员**：按模式二选一——Mode A/B/C 时用刀 5 审测试与验证产物；Mode D 时切换 Dr. Eggbot 视角审 Skill/Rules/Eval 防作弊与上下文预算。

主审负责剔除重复项、核实每一行引用与例外条款后再按第四节模板输出。

## 四、标准输出模板（Poteto Review Output Contract）

```markdown
# Poteto Review：<目标名称 / PR / 模块>

审阅模式：Mode <A/B/C/D>（只读诊断，未修改源文件）
雷达输入：<poteto_audit.py 摘要；无本地代码则注明“基于提供文本/Diff审阅”>

## 1. 主厨总评与门类判定
- **结论**：<放行 / 带条件放行 / 打回重塑>
- **核心病灶**（2-3 句直指环境或根因本质，不做风格寒暄）：...
- **单向门提醒**：<列出不可逆改动或人类拍板点；无则写“未发现不可逆单向门”>

## 2. 信任倒金字塔下沉建议表

| 当前问题 / 滞留层 | 风险说明 | 建议下沉层与具体落点（Tier 1 / Tier 2 / Tier 3） |
|---|---|---|
| ... | ... | ... |

## 3. 分级问题清单

### MUST KILL
- `<file:line>` `[分类]` — 问题事实、为什么它是毒瘤、最小删改做法。

### MUST RESHAPE
- `<file:line>` `[根因/架构]` — 症状与真实第一因、结构重塑方向。

### PROSE DEBT / FAKE PROOF / WEED BUFFER
- `<file:line>` `[标签]` — 证据与处置建议（`WEED BUFFER` 注明“留待缓冲队列满两处再治理，勿混入本 Diff”）。

## 4. 最小可验证下一步（最多 3 步）
1. **[先做]** <具体的删减/下沉/验证动作 + 完成判据>
2. ...
```
