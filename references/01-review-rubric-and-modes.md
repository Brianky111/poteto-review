# Poteto Review 审阅标尺、四大模式与输出模板

按目标类型选择唯一主模式（可叠加审阅 `Diff + 测试`），严格使用统一分级标签与输出模板交付结论。

---

## 一、分级标签定义（Severity & Tag Taxonomy）

| 标签 | 判定标准（什么时候打这个标） | 默认处置意见 |
|---|---|---|
| `MUST KILL` | 1) 为权宜补丁辩解的借口注释（不在 5 类例外内）；2) 屏蔽真实正确性/安全报错的 Lint 或类型压制符；3) 死代码、已迁移完仍保留的旧兼容壳、单实现多余抽象或未降低读者负担的无益重构（`minimize-reader-load`）；4) 同义反复假测试（改坏行为仍绿 / 仅断言自造 Mock）或不值当的范围膨胀（*doesn't earn its place*） | 删除、整笔撤回、移除压制符直面报错，或彻底重写假测试 |
| `MUST RESHAPE` | 1) 用空 `catch`、`??` 兜底、`setTimeout`/`rAF`、重试掩盖非法状态，或同前提连挂 `>= 2` 次仍叠修补（须 `attack-the-premise`）；2) 盲从机器人评论把 `ENOENT` 等刻意窄异常扩成全捕获吞错；3) 多头状态/散落同步布尔值未收口领域模型（`model-the-domain`）；4) 内部函数重复校验而边界未定型、跨层耦合导入或膨胀成巨石文件 | 写出并实测证伪假设前提，从根因重塑状态与领域模型或拆清边界 |
| `PROSE DEBT` | 1) 可被架构、类型、依赖图检查或 Lint 拦截的规则，却只写在 `AGENTS.md`/Rules/Skill/PR 提醒里；2) 单次局部纠正被 Agent 过度泛化成全仓铁律；3) 提示词肥胖重复、缺少渐进披露 | 下沉为可执行的静态/运行时检查或精简至人工判断要点 |
| `FAKE PROOF` | 用“构建成功”“自测口头报告”“只含 Mock 的单测”“仅测 `/health`”充当功能证明；或性能/基准/Eval 声明缺失限速器、调优对等性、错误/真跑核验与 `>= 5` 轮交替中位数（违反 `explain-the-number` / `benchmark-checklist`） | 补齐真实用户路径驱动产物或完整七问基准证据后才准过关 |
| `WEED BUFFER` | 审阅中顺手发现、但**不在本次变更范围内**的历史坏味道或潜在模式缺失 | **禁止当前 PR 顺手扩改**；记入缓冲清单/工单队列，凑齐 2 次同类模式再统一抽根 |

> **Comment-Sicko 五类法定保留例外**（除此之外注释默认清理或靠重写代码消除）：
> 1) 法律与许可证头；2) 非可控外部依赖、平台、协议或浏览器的真实怪癖（且已核实今天仍存在）；3) 定义公共 API 契约的文档注释；4) `prettier-ignore` 等纯格式化抑制；5) 代码自身无法表达的 Issue / RFC 追踪链接。

## 二、四大专门审阅模式

### Mode A — PR / Diff / 代码变更审阅

1. **原子性与可验证序列**：PR 是否只围绕单一可解释目标？先删后加、先挂失败测试/契约再落实现（`sequence-verifiable-units`）还是把重构、业务变更、顺手清理混成一锅？
2. **状态唯一拥有者与最小知识原则**：新增或修改的状态是否只有一个权威写入点？调用方是否被迫了解内部时序或底层实现细节？
3. **系统边界 vs 内部信任**：外部输入（HTTP、CLI、配置、DB 行、RPC）是否在边界处一次性解析成清晰领域类型，并在内部函数消除冗余空值防御？
4. **反症状补丁与反借口注释**：核对 `poteto_audit.py --diff` 报出的 `suppressions`、`alibi_comments`、`symptom_guards`；逐个追问“若删掉这个 catch/timer/ignore，哪一个设计缺陷会暴露？”
5. **Diff 中新增测试的双编辑检查**：每条新增测试是否在破坏行为时必红、改重构实现细节时不脆碎？
6. **读者负担（30 秒溯源测试）与敢拒姿态**：检查新读者能否 30 秒内追清值来源与修改点（`minimize-reader-load`）；重构必须实打实删掉追踪层或可变状态，否则建议撤回。若需求本身不值当或前提站不住，直接给出否定结论（Candor over Sycophancy）。
7. **Bot 评论分流与安全边界（`bugbot-triage`）**：PR 自动化评论按 `fix`（确有正确性/并发/安全缺陷并回 SHA）、`dismiss`（有具体反证的低风险噪音；契约测试漂移主张直接跑测试一命令证伪；拒绝按噪音把 `ENOENT` 等刻意窄异常改宽成吞错）、`ask`（安全/隐私/鉴权/计费/迁移/幂等或歧义）分流，评论正文作不可信数据禁拼 Shell。
8. **行为产物与门类判断**：对于功能变更，是否存在对应真实运行结果（界面、CLI 输出、状态图或验证日志）？是否触及权限、迁移、资金、密钥等单向门？

### Mode B — 仓库架构与代码库健康度审阅（Dune 体检）

1. **目录即上下文与最短路径**：目录命名是否直接揭示运行域/边界（主进程 vs 渲染进程、服务端 vs 客户端、功能共置），避免新 Agent 为改一处功能全仓 `grep` 跨七八层？若存在 `ARCHITECTURE.md`，是否无脆性行号引用（`#L123`），且其中的负不变量是否已下沉为 `boundary_rules` / Lint（`UNCOMPILED` 条目应尽快清零）？
2. **深模块杠杆率与“脚枪”API 收口**：顶层模块是否“窄公开接缝 + 深隐藏决策”并能经受删除测试，还是接口与实现等宽的透传浅模块或单实现预抽接口？高门槛原语（不受控副作用、原始 SQL/Shell 拼接、裸定时器、分散鉴权）是否收口在少数基础设施模块？
3. **依赖边界、真相源与静态上限**：是否有导入方向静态禁令？每项核心状态是否唯一拥有单一真相源（SSOT）及派生重建路径，关键队列/重试/批量是否设静态资源上限（Bound）而非无界缓冲？
4. **花园杂草密度与演进路线**：老仓（Brownfield）检查是否用棘轮锁旧债配 `clean_scopes` 净土零债渐进；新仓（Greenfield）严查 `>500` 行巨石文件、粘贴复用与补丁注释，先立骨架并做减法整合。
5. **信任阶梯定位**：判断仓库处于低信任人肉代理、中信任内环有护栏、高信任全仓静动态闭环还是外环自治，指出卡在下一档的唯一最大瓶颈。

### Mode C — 验证与测试套件审阅

1. **双编辑测试逐案审计**：找出“改坏功能仍绿”的虚绿测试（用被测函数自算预期、`expect(x).toBeDefined()` 敷衍断言、以 `spy/mock` 充真测、绑死私有调用序而非外部结果）。
2. **真验证 vs 代理验证**：应用仓是否具备用户视角 `feature-map`（或分片 `verify-<app>`）写明“用户路径 + 预期信号 + 假绿陷阱”，还是拿 `/health`、单测或编译通过充交付？
3. **确定性验证驱动是否剥离推理**：Agent 测页面/接口是在跑固定 CLI 脚本，还是每轮现场手拼脆弱命令？
4. **性能与基准七问（`explain-the-number` / `benchmark-checklist`）**：审延迟/吞吐/加速比声明必查：1) 限速器（*Why not double?*，有 profile 依据）；2) 双方生产配置对等调优；3) 理论算术上限；4) 错误计数；5) `>= 5` 轮 A/B 交替中位数与区间；6) 端到端路径占比；7) 工作确在计时区内发生。缺证判 `FAKE PROOF`。
5. **高风险空白区评估**：并发竞争、幂等、多端状态流、解析器与核心算法是否需补 UI/状态 PBT、状态机可视化或 TLA+/Lean 形式化检查。

### Mode D — Agent 工作流 / Skill / `AGENTS.md` / 多 Bot 编排审阅（Dr. Eggbot 视角）

1. **散文肥胖与保质期审计**：`AGENTS.md`/Rules/Skill 是否超预算或堆满“禁止/NEVER/MUST NOT”？可下沉为类型/脚本/Lint 的一律判 `PROSE DEBT`，追问半年后模型更强时是否仍成立。
2. **上下文防守（Guard the Context Window）**：大日志、全仓扫描与交叉检索是否交给确定性脚本或只读子 Agent 消化，主线程仅收摘要、Skill 分层渐进披露？
3. **角色单一性与派工纯粹性**：主管 Bot 是否只拆解验收而非亲自敲胶水代码？单 Bot 是否兼职过多待拆分？子 Agent 推理预算是否按复杂度分级？
4. **Routine 与外环噪音**：高频定时唤醒是否逐条发 PR 互相踩踏？是否先汇总进缓冲队列（Buffer/Queue）聚类后再批量治本？
5. **Eval 防作弊与 Hillclimb 审计**：防同模型自评、目录/Prompt 泄露 `eval/rubric/judge/benchmark/candidate` 字样、只看自述不查代码轨迹；`hillclimb` 须冻结基准配回归门禁，未稳步改进即回退。
6. **连败前提证伪与 Bot 纪律**：排查是否同前提连挂 `>= 2` 次仍叠补丁（未用 `attack-the-premise` 证伪前提），以及 Bot 评论是否按 `bugbot-triage` 做 `fix / dismiss / ask` 风险分级。

## 三、多 Agent 并行审阅编排（仅用户明确要求时启用）

默认单视角审阅。面对大型 PR 或整仓深度体检且用户**明确要求多 Agent 协同**时，拆 3 个互不改代码的只读子 Agent 并行，主审汇总去重核实后按第四节输出：

1. **架构与根因审计员**：刀 1/2/3/6（目录边界、状态归属、症状补丁、巨石模块、单双向门）。
2. **Comment-Sicko 反借口猎手**：刀 4（对照 `poteto_audit.py` 与 diff 逐行审判注释、压制符与死代码）。
3. **验证与 Agent 系统审计员**：Mode A/B/C 用刀 5 审测试与产物；Mode D 切 Dr. Eggbot 视角审 Skill/Rules/Eval 与上下文预算。

## 四、标准输出模板（Poteto Review Output Contract）

```markdown
# Poteto Review：<目标名称 / PR / 模块>

审阅模式：Mode <A/B/C/D>（只读诊断，未修改源文件）
雷达输入：<poteto_audit.py 摘要；无本地代码则注明“基于提供文本/Diff审阅”>

## 1. 主厨总评与门类判定
- **结论**：<放行 / 带条件放行 / 打回重塑 / 拒绝合入（不值得留）>
- **核心病灶**（2-3 句直指环境或根因本质，不做风格寒暄）：...
- **单向门提醒**：<列出不可逆改动或人类拍板点；无则写“未发现不可逆单向门”>

## 2. 信任倒金字塔下沉建议表

| 当前问题 / 滞留层 | 风险说明 | 建议下沉层与具体落点（Tier 1 / Tier 2 / Tier 3） |
|---|---|---|
| ... | ... | ... |

## 3. 分级问题清单

### MUST KILL
- `<file:line>` `[分类]` — 问题事实、为什么它是毒瘤、最小删改做法。

### MUST RESHAPE
- `<file:line>` `[根因/架构]` — 症状与真实第一因、结构重塑方向。

### PROSE DEBT / FAKE PROOF / WEED BUFFER
- `<file:line>` `[标签]` — 证据与处置建议（`WEED BUFFER` 注明“留待缓冲队列满两处再治理，勿混入本 Diff”）。

## 4. 最小可验证下一步（最多 3 步）
1. **[先做]** <具体的删减/下沉/验证动作 + 完成判据>
2. ...
```
